# Roman Urdu Notes - Website

YouTube video -> study notes in English or Roman Urdu (.docx + .txt). Visitors enter their own Gemini key and a video link, watch progress and logs on the dashboard, and download the files from there as soon as the job finishes.

```
frontend/   12 pages (home, tool, features, how-it-works, solutions, security, faq, about, contact, privacy, terms, 404)
            style.css, site.js, app.js, config.js, img/ (illustrations, logo, social image)
backend/    main.py (FastAPI), auth.py (accounts, Google), db.py (MySQL), yt_to_roman_urdu.py + yt_to_english.py (the two converter scripts)
tehreer.sql  database schema (tables) for MySQL - the database is called `tehreer`
tools/      build_pages.py  <- generates the website pages from your brand settings
Dockerfile, docker-compose.yml, Caddyfile        (deployment + automatic HTTPS)
docker-compose.apache.yml                        (app only, for use behind Apache)
deploy/     apache.conf, nginx.conf, roman-urdu-notes.service
```

The conversion prompt sent to Gemini and the generated Word document stay in Roman Urdu on purpose, since that is the product's output. Everything else (code, comments, logs, UI) is English.

## Brand name, domain and images
The site ships with the placeholder brand **Tehreer** (tehreer.com). Check that your chosen name and domain are available and not trademarked before buying.

To rebrand, edit the three lines at the top of `tools/build_pages.py` (`BRAND`, `DOMAIN`, `EMAIL`) and run:
```bash
pip install cairosvg          # optional: regenerates the social-share image (og-image.png)
python3 tools/build_pages.py
docker compose up -d --build  # (or restart the app)
```
This rewrites every page, the page titles, canonical links, the footer and the social-share image with your new name. Also set `PUBLIC_URL=https://yourdomain.com` in `.env` (used by `sitemap.xml` and `robots.txt`) and create the mailbox you put in `EMAIL`.

Images are original SVG illustrations in `frontend/img/` (hero, steps, use cases, security) plus the logo. To use your own photos or artwork, drop the files into `frontend/img/` and change the `<img>` file names in `tools/build_pages.py`.

## Design themes (the "Design" menu)
The header has a **Design** menu (after About) with five complete designs. The visitor's choice is saved in their browser (`localStorage`, key `site_theme`) and applies to every page.

| Theme | Look |
| --- | --- |
| Theme 1 - Classic | Navy and gold, serif headings (the default) |
| Theme 2 - Midnight | Dark mode, glass cards, electric blue and violet |
| Theme 3 - Corporate | Light, sharp corners, structured grid, blue |
| Theme 4 - Editorial | Ivory, forest green, terracotta, serif display type |
| Theme 5 - Vibrant | Bold gradients, floating pill header, violet and pink |

How it works: `frontend/style.css` is token based (`:root` = Theme 1; `[data-theme=t2]` ... `[data-theme=t5]` override tokens and a few layout rules). Illustrations are inlined into the pages with CSS-variable colours, and `frontend/themes.css` (generated by `tools/build_pages.py`) recolours them per theme. Theme fonts are loaded from Google Fonts only when that theme is selected.

To change the default theme for new visitors, edit the token values under `:root` in `style.css`. To edit a theme's colours, change the variables in its `[data-theme=tN]` block. To add Theme 6, add a block in `style.css`, an entry in `THEMES` (and `FONTS`) in `site.js`, and a colour entry in `THEME_COLORS` in `tools/build_pages.py`.

## Updating a running site
After replacing the project files with a newer version:
```bash
docker compose -f docker-compose.apache.yml up -d --build    # or: docker compose up -d --build
curl http://127.0.0.1:6550/api/health                        # "frontend_build" changes when the frontend changes
```
Then hard-refresh the browser (Ctrl+Shift+R). Pages, CSS and JS are served with `Cache-Control: no-cache` and versioned URLs, so browsers pick up new files after a rebuild.

## Accounts, MySQL and phpMyAdmin
Visitors create their own account, and only **Gmail addresses** are accepted. There are two ways in:

* **Register with e-mail:** first name, last name, phone, Gmail address, username and a complex password (at least 10 characters with upper and lower case letters, a number and a symbol). The site e-mails a 6-digit code to the Gmail address and the account becomes active only after the code is entered. Later the user signs in with Gmail + password.
* **Continue with Google:** one click. A verified Google account is enough; the account is created automatically (name and Gmail come from Google, a username is generated).

A forgotten password is reset with a code e-mailed to the Gmail address (this also lets a Google-only user add a password). Each account has its own workspace: the notes tool, a history of conversions with re-download, profile, change password and "delete my account". Everything is stored in MySQL, in the database **`tehreer`**. Passwords are stored only as Argon2 hashes.

```
users         one row per person (names, username, phone, Gmail, password hash, Google id, status ...)
login_codes   one-time e-mail codes for confirming a Gmail address and for password reset (hash only, 10 min, 5 attempts)
sessions      signed-in browsers (only a hash of the cookie token is stored)
jobs          every conversion of every user (title, status, file names, dates)
auth_events   sign-in audit trail
user_overview read-only view: users with their number of conversions (handy in phpMyAdmin)
```
The schema is in **`tehreer.sql`**. MySQL creates the tables on its first start (the file is mounted into the container) and the app also applies it at every start (all statements are `IF NOT EXISTS`, so it is safe). To create the database by hand: `mysql -u root -p < tehreer.sql`.

### 1. Configure (`.env`)
```bash
cp .env.example .env && nano .env
```
Set at least `SECRET_KEY`, `DB_ROOT_PASSWORD`, `DB_PASSWORD` and the `SMTP_*` e-mail settings.

**Sending the codes with Gmail:** create a dedicated Gmail account for the site (for example `yourbrand.noreply@gmail.com`), turn on 2-Step Verification, create an **App password** at https://myaccount.google.com/apppasswords and put it in `.env`:
```
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=yourbrand.noreply@gmail.com
SMTP_PASSWORD=the-16-character-app-password
```
Gmail limits how many e-mails an account can send per day. For a busy site use a transactional e-mail service (Brevo, Amazon SES, Mailgun ...) with your own domain: only the `SMTP_*` values change.

### 2. Turn on "Continue with Google"
**It is free** (no billing account or credit card is needed for Google sign-in) and works on your own server, but Google must know which website may use it, so you register the site once (about 5 minutes, steps below). On a live server Google only accepts a **domain name with HTTPS** (not a bare IP address); `localhost` is allowed for testing.

The button always shows; it works once you add Google credentials. The visitor clicks it, picks a Google account on Google's own page and comes back signed in: the account is created automatically from the Google profile (name, Gmail, profile picture), nothing to type. Google does not share phone numbers, so the phone field stays empty until the user adds it on the Account page.

1. Open https://console.cloud.google.com/ and create (or choose) a project.
2. **APIs & Services > OAuth consent screen:** choose *External*, fill in the app name and your support e-mail, save. While the app is in *Testing* only the test users you add can sign in; click *Publish app* when you go live.
3. **APIs & Services > Credentials > Create credentials > OAuth client ID**, type **Web application**.
4. Under **Authorized redirect URIs** add `http://localhost:6550/api/auth/google/callback` for local tests and `https://yourdomain.com/api/auth/google/callback` for the live site. The address must match exactly (open the site as `localhost`, not `127.0.0.1`, when testing).
5. Copy the **Client ID** and **Client secret** into `.env` as `GOOGLE_CLIENT_ID=...` and `GOOGLE_CLIENT_SECRET=...`, then restart: `docker compose -f docker-compose.apache.yml up -d --force-recreate app`.

Only Gmail accounts are accepted, even through Google. Keep the client secret private.

**Error "redirect_uri_mismatch" at Google?** The address in step 4 must match exactly. The app prints the exact address it uses: `docker compose -f docker-compose.apache.yml logs app | grep "redirect URI"`. Copy it into Google Cloud Console (same scheme, host and port, no trailing slash).

### 3. Start
```bash
docker compose -f docker-compose.apache.yml up -d --build      # or: docker compose up -d --build  (Caddy)
docker compose -f docker-compose.apache.yml logs -f app        # watch the start-up
curl http://127.0.0.1:6550/api/health                          # "db": true means MySQL is connected
```
**Testing on your laptop without e-mail:** in `.env` set `SMTP_HOST=` (empty) and `ALLOW_DEV_CODES=1`, restart, register an account (or use Forgot password) and read the code with `docker compose logs app | grep "code for"`. Never enable `ALLOW_DEV_CODES` on a public server.

### 4. phpMyAdmin (database dashboard)
phpMyAdmin runs next to the database and listens **only on the server itself**: `http://127.0.0.1:8081` (change the port with `PMA_PORT`). Log in with user `tehreer` and `DB_PASSWORD` (or `root` and `DB_ROOT_PASSWORD`), then open the `tehreer` database. Browse `users`, `jobs`, `auth_events` or the `user_overview` view.

From your own computer, reach a remote server's phpMyAdmin with an SSH tunnel (the safest way, nothing is published):
```bash
ssh -L 8081:127.0.0.1:8081 user@your-server      # then open http://127.0.0.1:8081
```
Or publish it on its own sub-domain **with a password and HTTPS** using `deploy/apache-phpmyadmin.conf` (Apache) or the commented block in `Caddyfile`. Never expose phpMyAdmin without a password.

### Backup and restore
```bash
docker compose -f docker-compose.apache.yml exec db sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" tehreer' > tehreer-backup.sql
docker compose -f docker-compose.apache.yml exec -T db sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" tehreer' < tehreer-backup.sql
```
The data lives in the `dbdata` Docker volume, so it survives rebuilds and restarts (it is removed only by `docker compose down -v`).

### Without Docker
Install MySQL 8, create the database and a user, then run the app with the `DB_*` variables:
```bash
sudo mysql < tehreer.sql
sudo mysql -e "CREATE USER 'tehreer'@'localhost' IDENTIFIED BY 'a-strong-password'; GRANT ALL ON tehreer.* TO 'tehreer'@'localhost';"
# put DB_HOST=127.0.0.1, DB_USER=tehreer, DB_PASSWORD=..., SECRET_KEY=..., SMTP_* in /opt/yt-roman-urdu-web/.env
```
The systemd unit in `deploy/` reads that `.env` file.

### Account-related settings
| Variable | Default | Meaning |
| --- | --- | --- |
| `SECRET_KEY` | random at start | Signs e-mailed codes. Set a fixed value in production |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | - | Credentials for "Continue with Google" |

| `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASSWORD` | db / 3306 / tehreer / tehreer / - | MySQL connection |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASSWORD` / `SMTP_FROM` | - / 587 | Mail server that sends the codes (`SMTP_SECURITY=starttls\|ssl\|none`) |
| `ALLOWED_EMAIL_DOMAINS` | gmail.com,googlemail.com | Which addresses may sign in (empty = any) |

| `SESSION_DAYS` / `CODE_TTL_MINUTES` | 30 / 10 | How long a session / a code stays valid |

Gmail addresses are normalised (dots and `+tags` are ignored), so `a.li@gmail.com` and `ali+x@gmail.com` are the same account.

**Upgrading an existing database:** the app adds the new columns (names, username, phone, password hash ...) automatically at start-up and keeps your data. Accounts created by the earlier code-only version have no password: those users choose *Forgot password* once to set one.

## Notes language: English or Roman Urdu
Before a conversion the tool page asks which language the notes should be in (two buttons: **English** and **Roman Urdu**). The form appears after one is chosen, and the choice is sent with the job. The backend then runs the matching converter script in its own process:

| Choice | Script | Result |
| --- | --- | --- |
| English | `backend/yt_to_english.py` | Clear, natural English notes (lectures in Urdu or Hindi are translated) |
| Roman Urdu | `backend/yt_to_roman_urdu.py` | Word-for-word Roman Urdu notes |

Both produce the same kind of Word + text files and print the same progress lines, so the progress bar, chunk strip, logs and downloads work for both. The language of every conversion is saved in the `jobs.language` column and shown as a badge on the Account page. To use other script files set `CONVERTER_SCRIPT_ENGLISH` / `CONVERTER_SCRIPT_ROMAN_URDU`. If you change the `print` messages of a script, keep the progress lines (`Processing Chunk 3/12`, `Chunk 3 completed`, `Converting the video in N chunks`) or update the patterns in `Job.feed()` in `backend/main.py`.

### How the converter scripts handle problems
Both scripts (`yt_to_english.py`, `yt_to_roman_urdu.py`) share the same safety behaviour:

* **Rate limits / overload (429, 503, 500):** Gemini is retried with growing pauses (15, 30, 60 seconds) instead of giving up after one pause.
* **Wrong or expired API key:** stops at once (no minutes of useless retries) and exits with an error.
* **A part that cannot be converted:** a visible `NOTE` box with the missing time range is written into the document, so a gap is never silent. Text that was already converted (the best attempt, or the good half of a split chunk) is always kept.
* **Nothing converted at all:** no empty document is produced; the script exits with an error.
* **Hidden control characters** in a transcript or Gemini answer are removed (they used to crash the Word export), and file names are cut to a safe length, so long Hindi / Urdu / emoji titles work.
* **Subtitles:** the `yt-dlp` fallback now also finds automatic captions when only other manual subtitles exist, and accepts `en-US`, `hi-IN` ... style language codes. Every Gemini request has a 180 second timeout.

## How it works
1. The browser sends `POST /api/jobs` (key + URL). The backend first verifies the key with Google.
2. Each job runs `yt_to_roman_urdu.py` in its own subprocess. The key goes only into that process's environment, never to disk or logs.
3. The script's logs are parsed line by line (`Processing Chunk 3/12`, `Chunk 3 completed`...) to produce the percentage, the chunk strip and the live logs.
4. The browser polls `GET /api/jobs/<id>` every 1.5 seconds. When the job finishes, the Word / Text download buttons appear.
5. Files are deleted automatically after `JOB_TTL_HOURS` (default 6).

Note: the backend matches these log lines, so if you change the `print` messages in the script, update the regexes in `Job.feed()` in `backend/main.py` too.

## Going live (Docker + automatic HTTPS) - recommended
1. Point your domain's **A record** to your server's IP and open ports 80 and 443.
2. On the server:
```bash
cp .env.example .env && nano .env      # DOMAIN=notes.yourdomain.com
docker compose up -d --build
```
3. Open `https://notes.yourdomain.com`. Logs: `docker compose logs -f app`. After changing files: `docker compose up -d --build`.

HTTPS is required because users' API keys travel from the browser to the server.

### With Apache (instead of Caddy)
Apache runs on the host as the public web server and proxies to the app on `127.0.0.1:6550`.
```bash
# 1. Stop Caddy if it is running (Apache needs ports 80/443)
docker compose down

# 2. Start only the app, bound to localhost
docker compose -f docker-compose.apache.yml up -d --build

# 3. Apache
sudo apt install -y apache2
sudo a2enmod proxy proxy_http headers rewrite ssl
sudo cp deploy/apache.conf /etc/apache2/sites-available/notes.conf   # change ServerName
sudo a2ensite notes && sudo apache2ctl configtest && sudo systemctl reload apache2

# 4. HTTPS (free certificate, needs a real domain pointing to the server)
sudo apt install -y certbot python3-certbot-apache
sudo certbot --apache -d notes.yourdomain.com
```
The Apache config sets an `X-Client-IP` header and the app reads it (`PROXY_IP_HEADER`), so per-IP limits cannot be bypassed by faking headers.
For a local test, use `ServerName localhost`, skip step 4 and open `http://localhost`.

### Without Docker (systemd + nginx)
```bash
sudo apt install -y python3-venv nginx certbot python3-certbot-nginx
sudo cp -r . /opt/yt-roman-urdu-web && cd /opt/yt-roman-urdu-web
python3 -m venv venv && venv/bin/pip install -r backend/requirements.txt
sudo cp deploy/roman-urdu-notes.service /etc/systemd/system/
sudo systemctl enable --now roman-urdu-notes
sudo cp deploy/nginx.conf /etc/nginx/sites-available/notes   # change server_name
sudo ln -s /etc/nginx/sites-available/notes /etc/nginx/sites-enabled/ && sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d notes.yourdomain.com
```

## Settings (environment variables)
| Variable | Default | Meaning |
| --- | --- | --- |
| `MAX_CONCURRENT_JOBS` | 2 | How many jobs run at once (the rest wait in a queue) |
| `MAX_ACTIVE_PER_IP` | 1 | Simultaneous jobs per IP |
| `MAX_JOBS_PER_HOUR_PER_IP` | 8 | Abuse protection |
| `JOB_TTL_HOURS` | 24 | How long finished files are kept |
| `MAX_JOB_MINUTES` | 180 | Hard time limit for one job |
| `TRUST_PROXY` | 0 (1 in compose) | Read the real client IP behind a proxy |
| `PROXY_IP_HEADER` | x-forwarded-for | Header the proxy sets with the client IP (`x-client-ip` for Apache) |

## Things to know
- **YouTube may block server IPs.** Transcripts fetched from a data-center IP often fail with "no subtitles" or a bot check. If that happens you need a proxy or cookies (not supported in the script yet).
- Run the backend with **a single worker** (job state is in memory). Restarting the server stops running jobs.
- Gemini quota is consumed from each user's own key, not yours.
- The Word file uses the font "Roboto Serif"; if it is not installed on the reader's computer, Word substitutes another font (change `FONT_NAME` in the script).
